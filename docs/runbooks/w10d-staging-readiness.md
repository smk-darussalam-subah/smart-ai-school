# W10-D recovery-only staging transaction

Status: SOURCE CANDIDATE - NOT DEPLOYED - INDEPENDENT REVIEW REQUIRED.

This is a deliberately narrow staging lane, not the general application release
pipeline. It rejects any `apps/` or `packages/` delta, missing/pre-existing failed
migrations, unavailable image, capacity below 24 GiB or 25%, or baseline drift.
Future application releases require a separately reviewed lane; there is no
implicit fallback to the old media/build/migrate/ingress workflow on failure.
Main's existing deployment script is unchanged and reachable only for main.

## Deployment preparation is a separate authorization

No host setup is performed automatically. Before a future deployment approval,
the operator must have verified and separately installed (where necessary):

- Source commit objects at the host, without moving its staging checkout; missing
  objects fail before mutation. No automatic fetch/bootstrap is hidden in this lane.
- Organization-private `ghcr.io/smk-darussalam-subah/diis-pg-backup@sha256:...` locally
  available, with RepoDigest, image ID, linux/amd64 platform and OCI revision bound.
  Registry manifest access must work through an existing minimum-read credential.
  Image revision must be an ancestor of deployment source and all four recipe/helper
  paths must be byte-unchanged. No build, pull, push or credential install here.
- Existing staging `.env.staging`, regular non-symlink single-link, appuser-owned
  mode 0600, contains one canonical unquoted `PG_BACKUP_IMAGE=<exact-reference>` line.
  No other setting is changed by this executor. Literal config bytes are hash-bound.
- Existing `/home/appuser/.local/state/diis-deploy`, canonical appuser-owned 0700,
  with existing `deploy.lock` regular appuser-owned single-link mode 0600. Uses the
  same host lock as the official deployment; no new lock route or override allowed.
- Private approval and media attestation below. `W10D_STAGING_APPROVAL_SHA256`
  environment/repository variable must bind exact approval bytes before the run.
  Variable setup and approval-file placement are future explicit changes, not done
  by this source session or by the executor.

The staging environment currently has no required reviewer. A merge can trigger
deployment; prepare bindings before separately authorized merge, never assume a
pending environment approval will stop an incomplete staging deployment.

## Approval schema (no dummy operational values)

File: `/home/appuser/.local/state/diis-deploy/staging-approval.json`.
Exact keys, duplicates/unknowns rejected, caller-owned 0600 with private parent:

| Field | Meaning |
| --- | --- |
| schema | `diis-staging-approval-v1` |
| sourceSha/sourceTree/baseSha | exact future staging SHA/tree and previous staging SHA; source must differ from base |
| imageRevision | approved image OCI revision, ancestor with unchanged image recipe/helpers |
| approvalId | unique 32 lowercase hex, nonzero; one-time receipt identity |
| notBefore/expires | integer UTC epoch, maximum one hour; ten minutes minimum remaining at entry/pre-mutation |
| backupImage/backupImageId/platform | exact approved GHCR digest / local image ID / `linux/amd64` |
| environmentSha256 | full raw private staging env bytes |
| legacySha256 | canonical legacy observation plus live cron/mounted shell/Python file hashes plus sorted mc/rclone/ZIP hash lines |
| sharedSha256 | canonical observations of Postgres, MinIO, Keycloak, nginx plus runtime nginx config hash |
| apps | exactly api/web, each `id`, `image`, `runtimeSha256` |
| modelSha256 | canonical projected two-service Compose model (unescaped semantic values) after removal of build/dependencies and pinning previous local image IDs/pull never |
| mediaEvidenceSha256 | full private media attestation bytes |

Canonical JSON uses sorted keys, compact separators and ASCII escaping, UTF-8.
Runtime observation hash includes ID, image, start/status, full mount/network
metadata plus in-memory selected runtime config and HostConfig. Environment entries
are sorted after duplicate-name rejection. Sensitive runtime fields never go to
stdout/log/report. Baselines must be obtained and reviewed through a separately
authorized private collector/operator; there is no public dump/auto-approve mode.
The source does not replace owner approval with self-generated baseline hashes.

Media file: same private directory, `staging-media-evidence.json`, exact keys:
schema=`diis-media-readonly-v1`, environmentSha256, expires matching approval,
status=`verified`, owner (nonempty role identifier <=80 chars),
scope=`existing-staging-media-only`. This is an external operator attestation,
not a live provider authorization proof generated by the deployer. The operator
must have verified existing staging bucket/policy/principal readiness read-only.
Its short expiry and env binding do not prove provider policy cannot change;
provider drift still requires a fresh observation, never fallback provisioning.

## Execution and effects

Actions sends exact checked-out Python source in memory through the existing SSH
action to appuser. No host code bootstrap/file is created. Production/test-root
environment selectors are forbidden. External commands use a fixed clean environment
and bounded stdout, discarded stderr, timeout, EOF and process-group absence proof.

Read-only guard runs before any writes and repeats under the existing lock. It checks
source/ref/ancestor/tree, registry/local image/platform, capacity, Postgres major 16,
exact applied migration-name set, app IDs/config, current Compose config hash labels,
legacy/shared fingerprints, media attestation and public health. Compose config hash
version drift fails closed; it is not normalized away. No backup or ingress helper runs.

Legacy bind sources may not overlap the staging tree in either direction. Every
mounted `.sh`/`.py` is hashed inside the running legacy container, as are cron and
available pinned tools. These are reads, not invocation of backup scripts. Actual
access to Docker/cron must be authorized; no sudo or privileged container workaround.

After recheck, an exclusive non-secret `staging-consumed-<approvalId>.json` receipt
consumes the approval. A private `staging-attempt-<approvalId>` directory contains
ownership journal, bounded env snapshot and projected rollback model. Files are
exclusive 0600; ownership exists before checkout or container mutation. Attempt 1
only, new workflow run cannot reuse the receipt. No automatic receipt deletion.

The only forward operational commands are exact `git merge --ff-only <sourceSha>`
and a two-service Compose up with `--no-deps --no-build --pull never`, retaining
approved previous app image IDs. The projected model contains only api/web and two
external networks, no mounts/devices/privilege/hooks/configs/secrets resources.
Only whitelisted model fields are accepted. No env mutation, DB init/migrate,
media/user/policy action, backup recreation, timer, BuildKit or ingress candidate.

Environment and explicit command/user settings must match live apps before mutation.
Compose serialization is decoded once and dollar-escaped once for reload; a
config-only round-trip contract verifies literal-dollar preservation without
creating a container. Full app runtime settings and image/network scope are compared
after apply. Strict runtime/Compose-version differences may stop commissioning;
they may not be weakened to make a baseline pass.

## Failure, rollback and cleanup

Health requires exact HTTP 200 on all four bound URLs; redirects are not followed or
accepted. After forward and rollback apply, readiness polls only health observations
for at most 90 seconds inside the existing operation deadline, without reapplying
Compose. Transient health failures may converge; permanent failures, signals and
exhausted command budget remain fail-closed. This does not relax preflight health.

Forward commands share a maximum ten-minute budget (further limited by expiry),
30-second observation limits and 120-second app-up limit. At least four minutes
forward budget must remain at mutation boundary. Bounded rollback has five minutes;
remaining expiry reserve is held for it. The SSH action caps the whole command at
20 minutes. SIGKILL/host loss cannot execute traps: receipt/journal retain ownership
for manual investigation. No promise of automatic recovery after host loss.

Failure/signal after mutation registration, only with proven producer cleanup, invokes the exact private model with
previous app image IDs. It never restores an env file blindly: executor never
changes it, and verifies bytes against snapshot; external drift stops rollback.
Legacy/shared drift also blocks rollback to avoid additional damage. Source checkout
is preserved for audit; no destructive reset/down-migration/production restore.
After rollback, health, app runtime, legacy and env must verify. Rollback success
remains FAILED/no-retry, not deployment success.

Child ownership is registered while handled signals are masked, inside the cleanup
scope, before selector setup. The mask remains throughout producer ownership;
the bounded loop observes pending signals and stops. Original mask restoration
occurs only after cleanup. Cleanup preserves the original signal dispositions:
it must not install SIG_IGN, which discards pending cancellation. Repeated signals
remain blocked during bounded TERM/KILL escalation, child reap and group-absence
verification, then propagate on unmask even after an otherwise successful command.
Cleanup ambiguity takes precedence over interruption during mask restoration.
Observer or resource-close failure is typed ambiguity, not an ordinary failed command.
Unresolved producer ownership blocks further commands and rollback; both snapshots
and journal remain private, with status 74 and retry prohibited. No automatic retry
or snapshot removal is permitted even if the producer may actually have exited.

Successful forward completion removes both sensitive snapshots, proves absence,
then removes journal/directory. Successful rollback removes sensitive snapshots and
retains journal; ambiguous rollback, interruption during preparation, or cleanup
failure retains private artifacts with status 74 for the owner. No success marker
precedes cleanup and lock release. Receipt remains intentionally. Retained artifacts
are not silently abandoned: inspect under a separately scoped recovery decision;
never run a fresh attempt or remove someone else's snapshots to clear the blocker.

registry authentication, SSH transport or real runtime rollback. Those proofs require

No deployment, publication or commissioning is authorized by this runbook.
